1Introduction and goals

CheesyBeez ERP lets a cashier take an order in seconds, the kitchen cook from a screen, and the owner see what needs attention from anywhere. Its POS module is in daily use at the shop. Full requirements: SRS sections 3.1 to 3.7.

1.1 Quality goals

PriorityQuality goal (ISO/IEC 25010)What it means here
1Reliability: availabilityThe shop sells, cooks and prints with no internet and through power cuts.
2Security: integrity and accountabilityNo recorded sale, payment or stock change can be altered; every manager change says who, when and how much.
3Performance efficiencyEvery tap answers in under 100 ms; cameras and reports never slow the counter.
4Interaction capabilityStaff with minutes of training never hunt and never err: one primary action, Undo instead of dialogs.
5Maintainability and flexibilityA team of four supports the shop remotely: one installer, automatic updates, rules written and tested once.

5.2 Level 3: components of the shop server

The HTTP API hands every pushed event to the validator, which checks its shape, its shop, and that the person had a session with a role allowed to record it. Only then is it appended.

6Runtime view

6.1 Scenario: the cashier sends an order

6.2 Scenario: the internet goes down

Steps 1 to 4 continue unchanged. The replicator retries quietly, backing off to every 5 minutes. When the line returns it asks the cloud for its last sequence number and sends everything newer, 100 at a time, so nothing is skipped or doubled. Online orders pause and the counter shows it.

6.3 Scenario: a manager cancels a sent item

Ctrl+M and the manager's PIN open manager mode. Delete on a sent line asks for a reason (keys 1 to 3). applyManagerChange() returns the new order, one audited event with totals before and after in cents, and the inverse for Undo. The kitchen shows the line struck through as Cancelled. Esc or 10 seconds idle leaves manager mode.

8Crosscutting concepts

ConceptHow it is done
8.1 Event sourcingEvery change is an event (id made on the device, shopId, type, actor, time, seq). Screens fold events into state. Undo is a new event. Nothing is ever rewritten.
8.2 Offline syncDevice outbox, idempotent push of up to 100 events, pull by seq, WebSocket stream. The cloud is asked for its last seq, so no bookmark can drift.
8.3 SecurityPIN login with roles; one shared rule mayRecord on screens and server; per-device sessions; owner PIN on setup with lockout; per-shop cloud token stored hashed; camera logins AES-256-GCM; frames in memory only.
8.4 Shared domainsrc/domain is pure TypeScript with no browser, disk or network access. Imported by the counter app, the shop server and the Cloud Worker; tested once.
8.5 Replaceable edgesOrderInterpreter (shorthand today, voice or LLM later), SuggestionsService, AuthService, EventStore (SQLite or MySQL).
8.6 MoneyInteger LKR cents. Discounts round once, half up, at order level. Sent lines keep their price when the menu changes.
8.7 Multi-tenancyshopId on every synced row, mapped to tenant_id; shop ids end in 4 random characters so shops never collide.
8.8 InternationalisationEvery label has English, Sinhala and Tamil slots; si and ta stay empty until the owner supplies them.
8.9 Logging and supportHealth endpoint, camera log with daily rotation (14 days, logins masked), remote support over AnyDesk.
8.10 TestingVitest unit and component tests, fakes for D1, cameras and the detector; 1,089 test cases run in CI on every pull request.

9Architecture decisions

Each decision is recorded as an ADR: context, decision, status and consequences.

ADR-001Store events, not editable rows Accepted

Context
Managers change sent orders; the owner needs to trust every number; devices go offline.
Decision
An append-only event log; current state is folded from events; Undo is a new event.
Consequences
Full audit trail and conflict-free offline merging. Screens must fold events; history grows without end, so a snapshot will be needed for large shops.

ADR-002Modular monolith on the counter PC, cloud as a copy Accepted

Context
Unreliable internet; four developers; remote support; no hosting budget.
Decision
One shop server process on the counter PC is the source of truth. A Cloudflare Worker keeps a copy for phones and backup. Microservices were rejected.
Consequences
Selling never depends on the internet; one program to install. The counter PC is a single point of failure, covered by the cloud copy.

ADR-003SQLite by default, MySQL optional Accepted

Context
MySQL was the hardest part to install automatically on the shop PC.
Decision
Built-in SQLite behind the same EventStore interface; MySQL when DATABASE_URL is set. Same append-only triggers on both.
Consequences
Zero-setup install. One writer per shop.

ADR-004One pure domain library everywhere Accepted

Context
The same rules (prices, permissions, kitchen tickets) must agree on screen, server and cloud.
Decision
All business rules in src/domain as pure TypeScript, imported by all three.
Consequences
Rules are written and tested once. Domain code may not use the browser, disk or network.

ADR-005Heavy work in low-priority child processes Accepted

Context
Camera detection and the owner's digest take seconds of CPU; receipts must never wait.
Decision
Run them as child processes at below-normal priority over IPC; cap camera work at 50% CPU and slow it when over.
Consequences
The counter stays fast. Restart and health handling are needed for each child.

ADR-006Print through the Windows queue, not WebUSB Accepted

Context
WebUSB needs the printer's Windows driver replaced, which breaks normal printing.
Decision
The shop server sends raw ESC/POS to the Windows print queue; the drawer opens through the printer.
Consequences
The driver stays intact. The printer must be on the server's PC.

ADR-007Kitchen works from the screen only Accepted

Context
Owner's decision on 10 October 2026; changes and cancellations must reach the kitchen at once.
Decision
No printed kitchen tickets. The counter PC flips to the kitchen view with F2 until a kitchen device is added.
Consequences
Live changes with chime and flash. The kitchen depends on the screen being visible.

ADR-008AI only suggests Accepted

Context
A wrong action at the counter is worse than none.
Decision
Voice and LLM pick one command from a fixed list; the model is chosen by measurement (24 requests, Mistral Small 3.1: 23 right, no wrong page).
Consequences
Safe and replaceable. Less capable than an agent that acts on its own.

ADR-009Camera Shadow mode removed Superseded

Context
Shadow mode recorded camera guesses without moving tables, to compare with staff for a week.
Decision
Owner, 27 October 2026: computer vision is Off or On; old Shadow events read as Off.
Consequences
Simpler page. Camera accuracy is no longer measured automatically before going live.
