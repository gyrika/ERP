# ERP · POS module — architecture v0

## Decisions
- **Client:** TypeScript PWA (installable on tablets/phones, one codebase for counter, kitchen, owner). Not native: no app-store friction, instant updates for a 4-person team.
- **Offline-first:** the device is the first database (IndexedDB). Every action writes locally, then appends to an **outbox**; a background sync pushes it. Sales never wait on the network.
- **Server:** Node + **MySQL** (team knows it). Each shop = `tenant_id` on every row, enforced in every query. Orders use client-generated UUIDs so offline devices never collide.
- **Realtime:** WebSocket fan-out (counter → kitchen → owner phone). Falls back to polling.
- **Money:** integer LKR cents only.
- **Eat first, pay after** (owner, 2026-10-10): an order goes to the kitchen on **Send**, waits under "Waiting to pay", and is charged later. Later rounds go as separate "Added" tickets; sent lines are locked. Paying sends anything unsent, and never recalls kitchen tickets.
- **Kitchen works from the screen only** (owner, 2026-10-10): there is no printed kitchen ticket and no printed cancel slip, and no ticket-printing data is prepared. The kitchen therefore needs a screen it can always see (a second monitor, or a spare phone or tablet at `/#kitchen`). Every arrival, change and cancellation plays a short chime and flashes the ticket until the kitchen taps it. This replaces the earlier "kitchen printer fallback" rule. The thermal printer is for the **customer receipt and the cash drawer only**.
- **Changing sent items** (owner, 2026-10-10): only a manager or owner, with their PIN, may change (size, extras, quantity) or cancel an item already sent. The cashier keeps only the quick Undo straight after Send (the next action or the 6 s toast timeout seals the send). Adding items stays open to everyone ("Added" ticket). Voiding or editing a sent item still needs a short reason (owner, 2026-10-11, kept over the manager-mode spec's one-key void). The kitchen sees **Changed** with the old item struck through in red beside the new one, or the item struck through in red with **Cancelled**; the ticket reopens even if already Done.
- **Manager mode** (branch `manager-mode`, 2026-10-11; replaces the old one-change "Ask manager" flow): **Ctrl+M** (or the corner **Manager** key) → PIN → the order card lifts with a spring, a soft depth and a thin gold edge, a quiet clunk plays, and the corner reads "Managing · <name>". Arrows select a line, **Enter** edits, **Delete** voids (a sent line asks for a reason inline: keys 1-3), **P** takes cents off one line, chips **1/2/3/4** = 10% / 20% / 50% / Free (comp), **Ctrl+Z** undoes the last manager change, **Ctrl+K** opens the command palette. **Esc** or **10 s idle** returns to cashier mode (the spring reverses). No dialogs, no banner, no PIN per action. Every change stamps "Edited by <name>, <time>" on the order. Manager Undo works only inside the manager session; the cashier can never undo a manager change. Out of scope: menu prices, menu items, staff (owner only). Discounts on paid orders (refunds) are not built.
- **Money with discounts** (`src/domain/totals.ts`): menu prices never change; adjustments live on the order. total = subtotal − per-line adjustments − order discount; a percentage rounds **once**, half up, in integer cents, at the order level; Free = the whole remainder. A test checks every amount up to Rs 2,500 against exact arithmetic. A comped order closes with tender `comp` at 0.
- **One function for manager changes:** `applyManagerChange()` (`src/domain/manager.ts`) returns the new order, exactly one audit event (who, when, before/after in cents, and line before/after or reason) and the inverse used by Undo. The register calls it only through `manage()`, which also tells the kitchen and returns the Undo. Undo is a new `order.change_undone` event: nothing is ever rewritten.
- **Auth (SCRUM-40/41, built):** `AuthService` (`src/domain/auth.ts`). A paired device uses `serverAuth` (PIN checked by the server, which records each login as a session); development and the demo use `fakeAuth`. `src/services/auth.ts` picks one. The rules of who may record what (`mayRecord`) are shared by the screens and the server; the server stores an order event only if its person had a session on that device covering the event's time with a role that allows it. Lock screen with F4 to switch and a 5-minute idle lock; a kitchen login or kitchen device sees the Kitchen only. Staff are managed with `npm run server:staff` until the Owner view exists. `requireManager()` stays the single manager check.
- **Fake data:** all of it in `src/fake/data.ts` (staff + PINs, shop id, demo orders). `/?demo` loads the demo orders into a separate storage namespace (`cb.demo.*`), so real orders, kitchen and log are never touched.
- **shopId:** every synced row carries it: every event (stamped by the event log) and every kitchen ticket. The server maps it to `tenant_id`. The register's working snapshot is a device-local cache rebuilt from events by the server, so it does not.
- **Inventory (from PR #14, made event-based):** the item and supplier list is the owner's March 2026 price list, in code (`src/domain/inventoryData.ts`). Stock counts and working prices are events (`stock.adjusted`, `stock.price_set` with before/after cents, `orderNumber` 0), folded by `inventoryFromEvents`, so they reach MySQL and the cloud with who did them. Managers and owners only: the screen sends anyone else to the Register, and the server refuses a cashier's stock events.
- **Event log:** append-only, `src/domain/events.ts` (types) + `src/ui/eventLog.ts` (device store; becomes the sync outbox in slice 4). Events: `order.sent`, `order.send_undone`, `order.paid`, `order.payment_undone`, and the audited manager events `order.item_changed`, `order.item_cancelled`, `order.line_removed`, `order.line_adjusted`, `order.discount_set`, `order.comped`, `order.change_undone`. Each has id, shopId, actor, time and order number; manager events add totalBefore/totalAfter in cents.
- **"Table N needs cleaning" note** (owner, 2026-10-26, SCRUM-182): the one exception to "no banners". When a table comes to need cleaning, the Register shows that line for 5 s and it goes by itself: the Undo toast's look and place (bottom left, above the Undo toast when both show), `aria-live="polite"`, no button, no key, no focus, no taps (`pointer-events: none`), hidden under an open sheet or the palette like the toasts, so it never covers the order or the primary action. The Tables chip turns red (`--bad`) while any table needs cleaning.
- **Identifying orders:** by order number only. No name or phone field until the CRM + loyalty card slice; build nothing for it before then.
- **Input layer:** screens depend on `OrderInterpreter` only. Today: `ShorthandInterpreter` (rules, offline, instant). Later: voice / LLM implementing the same interface.
- **Intelligence:** a `SuggestionsService` interface (prep load, stock, anomalies, pricing) with a simple rules engine first; swappable later.

## Shop server storage and setup (2026-10-12)
- **Built-in SQLite by default** (`server/sqliteStore.ts`, `server/sqlite/*.sql`, applied on start): no database to install on the shop PC. Same `EventStore` interface and append-only rules (triggers) as MySQL; MySQL remains when `DATABASE_URL` is set. Chosen by the user because MySQL was the hardest part to install automatically.
- **Setup wizard** (`src/ui/SetupWizard.tsx`, `server/setup.ts`, settings in `server/data/settings.json`): shop → printer (switchable while running) → staff (owner first) → devices. Answers localhost only; after setup every change needs the owner's PIN (5 wrong → 30 s). The shop PC pairs itself as the counter; QR codes pair a kitchen tablet (LAN link) and the owner's phone (the shop server asks the cloud, `POST /api/v1/devices`, for a read-only owner token; `DELETE` withdraws a lost phone).

## Visual Flow (2026-10-24)
- **What:** sidebar › Things › **Visual Flow** (`#flow`, `#flow/<item>`; owner only, like the recipes; each opening is a `recipe.viewed`). One item in focus (a dish and size, an extra, or a batch), drawn with React Flow (`@xyflow/react`, lazy-loaded so the Register bundle is unchanged): bought items on the left, through his semi-processed items (culture → dough batch → dough ball), into the dish. Views: **Material** (how much per item), **Cost** (materials, electricity, labour, overhead; lines as thick as the money), **Financial** (price, whole cost, profit, and the last 28 days' sales from `order.sent`).
- **Pure core:** `src/domain/visualFlow.ts` builds nodes, edges, totals and layout from the same answers and prices as `costing.ts` (materials equal the Recipes screen's food cost). Tests: `visualFlow.test.ts`, `src/ui/visualFlow.ui.test.tsx`.
- **Editing:** drag a line from an item into a recipe, or use the panel (add an ingredient, add a stage, take a line out, batch size, amount, unit, **wastage**). Wastage is an optional `waste` share on a recipe line (`BookLine`): a line takes `qty / (1 − waste)` in cost and in stock (`grossQty`).
- **Resources:** `src/domain/resources.ts`. Per recipe (`resources:<recipe key>`): electricity (kWh), labour and equipment (minutes), other costs (Rs), per batch or per dish; the shop's rates once (`rates:shop`, Rs per kWh / per hour). Resources roll up through batches into each dish. Food cost (`menuCost`) stays ingredients only.
- **Draft and published:** every change is a `recipe.draft_set` (owner only, synced, kept like answers; checked for shape by the server, `checkDraft`). Drafts change no cost and no stock. **Publish** writes one `recipe.answer_set` per draft (a new version, `versionsOf`), which closes it; Undo writes the old versions back and reopens the drafts. Sales and waste already use the answers in force when they happened, so publishing never changes past production.

## Production with dependencies (2026-10-25, SCRUM-161)
- **One ledger:** `stockFromEvents` (`src/domain/inventory.ts`) now also returns a `ledger` (`src/domain/production.ts`): for raw (`stock:<id>`), semi-processed (`semi:<key>`) and, through `canMake`, finished items, what is on hand, held by batches in the kitchen, free, coming and short. Items and Visual Flow read it through `itemStockOf` (`src/domain/itemStock.ts`), so both show the same figures. A never-counted raw item is unknown and never holds production back; a semi-processed item with no batch made has nothing on hand.
- **Send to kitchen plans the chain** (`planProduction`): what the item is made from and is not there goes first, in whole batches, down every level; batches already coming and not spoken for are counted on (no duplicates). The item is sent held (`prep.ordered` with `waitFor`), so it is not on the kitchen screen.
- **Release on the server:** `releasesDue` (`src/domain/scheduler.ts`) runs on the shop server after every stored push (`server/scheduler.ts`), oldest first, and writes `prep.released` (id `rel-<ticket>`, so once). The server is on the counter PC, so it works offline; a device with no server (the demo) runs it itself. Devices cannot push a release. Chosen over releasing in each device's fold because the kitchen screen only folds a day of events and stock needs the whole history.
- **Cost:** the server keeps the shop's history in memory for this and folds it only while a batch is held. Fine for one shop; a big history would want a snapshot.

## CV tables (2026-10-26, SCRUM-164)
- **Domain (SCRUM-166; rules v2 SCRUM-182, the owner's of 2026-10-26):** `src/domain/tables.ts`, pure, time passed in. The worker calls `observe(tracker, {at, present, confidence?}, timers) → {tracker, change}` per frame and records `change` as `table.state_changed`. Free/reserved → occupied on the first frame with a foot point in the zone; occupied → left once empty `leftCheckS` (10 s; a person back sooner continues the visit); a visit (occupied since → first empty frame) under `shortVisitS` (3 min) → free, else needs_cleaning; needs_cleaning → free `autoFreeS` (5 min) after it began (`autoFreeAt` says when, Live with a camera only). A staff change (`staffSet`, also for Undo) holds until presence next flips, then that frame is judged by the rules; the auto-free is a time rule and applies under a hold too (choice: staff who freed a table people sit at are believed until those people leave). `cameraLost`: the table keeps its state, no left check or auto-free until frames return. `tablesFromEvents` folds the floor; `table.state_set_undone` is its Undo. Events carry no password or image (the server takes exactly their fields).
- **Timers (SCRUM-182):** `vision.settings_set` carries `shortVisitS` (0-3600), `leftCheckS` (1-300), `autoFreeS` (60-7200) instead of `seatS`/`leaveS`/`cleanAlertS`; `cleanAlertS` went (the chip is red as soon as a table needs cleaning, and it frees itself). Old events still pass `checkTableEvent` (all three old keys, never mixed with the new) and fold to their mode and CPU limit with the default timers: the old windows mean nothing under the new rules. The owner sets the timers in Cameras setup ("A visit shorter than this needs no cleaning", "Empty this long counts as left", "Free again by itself after"). The "why" line on `#vision` speaks the new rules ("Seen at 18:02; occupied 12 min", "Left at 18:40 after 38 min; frees itself in 4 min"); the 10 s left check lives in the worker's tracker only, not in events, so it is never shown as running. The Shadow week ignores a table freeing itself (the clock, not a sighting).
- **Vision role (SCRUM-167, 2026-10-26):** `vision` is a `Role` but never a person (`STAFF_ROLES` excludes it; setup, `server:staff` and PIN login refuse it). It may record only what the camera sees (`VISION_RECORDS` in auth.ts) and staff may not record those. No device push may carry it: the camera worker (SCRUM-170) hands its events to the server over IPC, and the server stamps `vision` and stores them itself, the way `server/scheduler.ts` stores `prep.released` with `store.push(device, made, now())` after the push, past `refusal` (then broadcast like the scheduler's releases).
- **Register floor (SCRUM-168, 2026-10-26):** the Tables chip (free count; red while a table needs cleaning, SCRUM-182) and `#tables`, one tile per table by number. **F1**, not F3 (F3 is the Owner view). Keys C cleaned / F free / R reserved / O seated (added so the floor works with no cameras) and Ctrl+Z, each a `table.state_set` / `table.state_set_undone` event. No layout (`table.layout_set`, set up in SCRUM-171) → no chip; `/?demo` seeds six tables (`src/fake/data.ts`). The chip, the fold and the floor are lazy chunks: the Register grew 1.6 kB (demo seed and loaders).

- Kitchen screen: none yet. Until the owner adds a kitchen device, the kitchen view runs on the counter PC itself: **F2** (or the corner **Kitchen** chip, which shows how many orders are cooking and the oldest wait, dot in the urgency colour) flips the whole screen between Register and Kitchen in the same tab (`src/ui/Root.tsx`). In the Kitchen: **Space** bumps the oldest ticket, **Ctrl+Z** undoes, **Esc**/F2 returns. A device opened straight at `/#kitchen` shows no Register key. Consequence: the sync server (slice 4) is not needed for the kitchen until that device arrives; it is still needed for safe storage, backups and the owner's phone.
- Printer: Xprinter XP-80T, 80 mm thermal, ESC/POS, USB to the PC. Network port not confirmed.
- Cash drawer: RJ11 into the printer; opened by an ESC/POS kick command sent with the receipt.
- Counter PC: Windows 10 Pro (out of Microsoft support since Oct 2025).
- Payments: no card machine; customers pay cash or bank transfer. "Bank transfer" tender added; Card and QR buttons stay and get real integrations later.
- Decision: printing and the drawer kick go through a local helper program (SCRUM-71) that sends raw ESC/POS to the Windows printer queue. WebUSB was rejected: it needs the printer's Windows driver replaced, which breaks normal printing.
- Flow: customers eat first, pay after (confirms Send to kitchen → Charge).
